# 발표 시연 · 팀 사용성 점검

## 준비

1. 저장소 루트에서 `python run.py` → http://127.0.0.1:8000.
2. **서버를 켠 뒤 1~2분** 기다려 머리글이 'OCR 엔진 준비 중'에서 '대기열 비어 있음'으로 바뀌는지 확인.
   PaddleOCR 는 처음 불러오는 데 시간이 걸립니다.
3. 실제 개인정보 대신 내장 가상 샘플이나 합성 송장(`samples/out/`)을 씁니다.
4. 발표할 Chrome/Edge에서 미리 한 번 저장까지 해 보고 결과 파일을 열어 봅니다.
5. 결과는 실제 OCR 분석이지만 **합성 데이터 기준**이라고 설명합니다. 성능 수치는 실사로 다시 재야 합니다.

## 90초 시연 대본

| 시간 | 조작 | 설명 |
|---|---|---|
| 0–15초 | 샘플 ‘택배 송장’ 클릭 | “사진을 올리면 서버가 글자를 읽고, 주변 문구로 개인정보인지 판정합니다.” |
| 15–30초 | 목록의 ‘휴대전화번호’ 클릭 | “‘연락처’ 옆이라 가림 권장, 같은 송장의 고객센터 번호는 공개 번호라 참고입니다.” |
| 30–45초 | ‘함께 노출됨’ 안내 가리키기 | “같은 종이의 이름·전화·주소는 서로 연결될 수 있다고 알려 줍니다. 다른 종이끼리는 묶지 않습니다.” |
| 45–60초 | ‘모두 선택’ 후 참고 항목 해제 | “기본으로는 아무것도 고르지 않습니다. 오탐 하나가 사진을 망치기 때문입니다.” |
| 60–75초 | ‘가림 결과’ → ‘전후 비교’, 흐리게 ↔ 검은색 | “미리보기는 서버가 저장할 때와 같은 방식으로 만든 것입니다. 흐리게도 원래 글자를 되살릴 수 없습니다.” |
| 75–90초 | 저장 | “저장한 파일을 서버가 다시 검사해, 가린 곳에서 읽히는 게 없는지 확인합니다. 위치정보도 지웁니다.” |

추가로 보여 줄 만한 것:

- 기울어진 송장 사진 — 박스가 글자를 따라 기울어지고, 가림도 그 모양대로 됩니다.
- 판정 조건 ‘정규식만’ — 고객센터 번호까지 전부 가림 권장이 되는 것을 비교로 보여 줍니다.

## 팀 사용성 점검

| 상황 | 확인할 것 |
|---|---|
| 내 사진(JPEG, 위치정보 있음) | 저장 영역의 위치정보 안내, 저장 후 '위치정보 제거됨' |
| 아무것도 안 고르고 저장 | 메타데이터만 지운 파일 |
| 분석 중 취소 / 사진 바꾸기 | 이전 요청이 대기열에서 빠지는지 |
| 여러 명이 동시에 분석 | ‘대기 N건 · 약 N초’ 표시 |
| 놓친 정보 | ‘영역 추가’로 그린 뒤 저장 |
| 390px 모바일 폭 | 목록·좌표 편집이 넘치지 않는지 |
