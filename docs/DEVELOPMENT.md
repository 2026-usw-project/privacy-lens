## 빠르게 실행

```bash
pip install -r requirements.txt
python run.py
```

`run.py` 가 환경을 먼저 점검한다. 패키지·한글 폰트·Tesseract·한국어 데이터를
확인하고, 없으면 운영체제에 맞는 설치 방법을 알려준 뒤 멈춘다. 샘플 이미지도
없으면 만들어준다. 통과하면 http://127.0.0.1:8000 로 서버가 뜨고, 같은 주소에서
화면(`web/frontend-demo`)까지 나온다.

PaddleOCR 를 권장한다(아래 "OCR 엔진 교체"). Tesseract 보다 한국어를 훨씬 잘 읽는다.

점검만 하려면 `python run.py --check`.

### Tesseract 설치

| | |
|---|---|
| Windows | [UB-Mannheim 빌드](https://github.com/UB-Mannheim/tesseract/wiki) 설치. **설치 중 Additional language data 에서 Korean 을 반드시 선택.** |
| macOS | `brew install tesseract tesseract-lang` |
| Linux | `sudo apt install tesseract-ocr tesseract-ocr-kor` |

Windows 설치 프로그램은 PATH를 잡아주지 않는 경우가 많다. `pipeline/ocr.py` 가
기본 설치 경로를 훑어서 찾는다. 그래도 못 찾으면 `PL_TESSERACT` 환경변수에
exe 경로를 지정하면 된다.

한글 폰트는 샘플 생성에만 쓴다. Windows 맑은 고딕, macOS Apple SD Gothic Neo,
Linux Noto CJK / 나눔고딕을 자동으로 찾는다. 리눅스에 없으면
`sudo apt install fonts-nanum`.

### 개별 실행

```bash
python samples/make_sample.py samples/out   # 샘플만
python server.py                            # 서버만
python -m eval.compare samples/out          # 비교 실험
python -m pytest tests                      # 테스트 (OCR 없이 돈다)
```

iPhone HEIC 사진은 `pillow-heif` 가 깔려 있으면 받는다. 휴대폰 사진의 EXIF 회전
정보는 분석 전에 화소에 반영한다.

### 화면

화면 소스는 `web/frontend-demo/dist/`(HTML·CSS·JS, 의존성 없음)이고, 서버는 이것을
한 파일로 묶은 `web/frontend-demo/privacy-lens.html` 을 `/` 로 내준다.
**dist 를 고친 뒤에는 반드시 다시 묶는다.**

```bash
cd web/frontend-demo
node scripts/check.mjs            # 문법·요소 참조·파일 형식·샘플 (정적 검사)
node scripts/check-contract.mjs   # 서버 결과 → 화면, 화면 → 서버 요청, 통신 오류
node scripts/build.mjs            # dist → privacy-lens.html
```

| 파일 | 역할 |
|---|---|
| `dist/api.js` | 서버 통신. `/analyze` `/redact/preview` `/redact` `/queue` `/queue/cancel` |
| `dist/core.js` | 서버 결과를 화면 영역으로, 고른 영역을 서버 boxes 로 |
| `dist/app.js` | 업로드·샘플·결과 목록·영역 편집·대기열 표시·미리보기·저장 |
| `dist/index.html`, `dist/styles.css` | 화면과 디자인 (`DESIGN.md`) |

사진은 브라우저에서 다시 그린 PNG 가 아니라 **원본 파일**을 보낸다. 다시 그리면
위치정보(EXIF)가 사라져 서버가 GPS 를 찾지 못한다. 가리기·미리보기·검증은 전부
서버가 하고, 화면은 그 결과를 보여 준다.

### OCR 엔진 교체

```bash
pip install paddleocr "paddlepaddle<3.3"

# Windows
set PL_OCR=paddleocr
python run.py

# macOS / Linux
PL_OCR=paddleocr python run.py
```

`pipeline/ocr.py` 의 `PaddleBackend` 는 **2.x / 3.x 를 모두 지원한다.**
3.x에서 API가 크게 바뀌었기 때문이다.

| | 2.x | 3.x |
|---|---|---|
| 방향 분류 인자 | `use_angle_cls` | `use_textline_orientation` |
| 로그 | `show_log` | 삭제됨 |
| 호출 | `.ocr(img, cls=True)` | `.predict(img)` |
| 결과 | `[[quad, (text, conf)], ...]` | `rec_texts` / `rec_polys` / `rec_scores` |

버전을 고정하는 대신 생성자 시그니처를 들여다보고 지원하는 인자만 넘긴다.
결과도 두 형식을 다 받는다. 사용자가 어떤 버전을 깔았는지 알 수 없기 때문이다.

문서 방향 분류(`use_doc_orientation_classify`)와 왜곡 보정(`use_doc_unwarping`)은
꺼둔다. 추가 모델을 내려받아야 하고, 스캔 문서용이라 생활 사진에는 맞지 않는다.
줄 단위 방향 분류만 켠다.

첫 실행 때 모델 가중치를 내려받는다. 오프라인이면 미리 받아둘 것.
`paddleocr` 만 깔고 `paddlepaddle` 을 빠뜨리면 모델 다운로드까지 진행된 뒤
`Engine 'paddle_static' is unavailable` 로 멈춘다. 둘 다 깔아야 한다.
`paddlepaddle` 3.3.x 는 CPU(oneDNN) 추론에서 `NotImplementedError:
ConvertPirAttribute2RuntimeAttribute not support` 로 죽는다. 3.2.2 로 확인했다.

#### 모델 고르기 (3.x)

| 환경변수 | 기본값 | 예 |
|---|---|---|
| `PL_PADDLE_LANG` | `korean` | |
| `PL_PADDLE_DET` | `PP-OCRv6_medium_det` | `auto` (= PaddleOCR 가 lang 으로 고르는 것) |
| `PL_PADDLE_REC` | lang 기본값 | `korean_PP-OCRv5_mobile_rec` |

기본 조합은 `PP-OCRv6_medium_det` + `korean_PP-OCRv5_mobile_rec` 다.
`PL_PADDLE_DET=auto` 면 PaddleOCR 3.7 이 `lang=korean` 으로 고르는
`PP-OCRv5_server_det` + `korean_PP-OCRv5_mobile_rec` 로 돌아간다.

검출기 비교. 합성 송장 3종 × 원본/책상 사진을 돌려가며 정답 숫자(전화·주소 번지·
동호수)를 몇 개 읽었는가. 각도당 18개.

| 각도 | 0° | 30° | 45° | 90° | 135° | 180° | 270° | 합계 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| `PP-OCRv5_server_det` | 18 | 18 | **10** | 18 | **7** | 12 | 18 | 101/126 |
| `PP-OCRv6_medium_det` | 17 | 18 | **18** | 18 | **0** | 12 | 18 | 101/126 |

합계가 같고 v6 가 1.5배 빨라서 v6 를 기본으로 했다. 다만 실패하는 각도가 다르다.
v6 는 비스듬히 **뒤집힌** 종이(135°)를 하나도 못 읽는다. 그런 사진이 많으면 `auto`.
둘 다 180°(거꾸로)에서 1/3 을 놓친다.

**PP-OCRv6 는 한국어를 지원하지 않는다.** v6 의 50개 언어는 중국어·영어·일본어와
라틴 문자 46개다. `PP-OCRv6_medium` 은 언어를 지정하지 않았을 때의 기본값일 뿐,
`lang=korean` 이면 v5 로 내려간다. 한국어 인식은 `korean_PP-OCRv5_mobile_rec` 가
최신이다. 검출은 언어를 덜 타므로 v6 검출기를 섞어 쓸 수 있다(위 표).

함정 하나: PaddleOCR 3.x 는 모델 이름을 **하나라도** 넘기면 `lang` 을 무시한다.
검출만 바꾸면 인식이 한국어를 모르는 `PP-OCRv6_medium_rec` 로 떨어진다.
`PaddleBackend` 가 빠진 쪽을 lang 기본값으로 채워서 막는다.

실제로 쓴 모델 이름은 화면 하단 정보 줄과 `eval.compare` 첫 줄에 나온다.

```bash
# 비교 실험: 규칙은 같고 모델만 다르다
PL_OCR=paddleocr python -m eval.compare samples/out
PL_OCR=paddleocr PL_PADDLE_DET=PP-OCRv6_medium_det python -m eval.compare samples/out
```

## 설계 원칙

이 프로젝트에서 지키기로 한 것들. 코드보다 이쪽이 중요하다.

### 1. 확실성과 심각도는 별개의 축

흐릿한 학생증은 **심각도 높음 / 확실성 낮음**이고, 선명한 고객센터 번호는
**확실성 높음 / 심각도 낮음**이다. 두 값을 하나의 점수로 합치면 둘 다 망가진다.

`types.py`의 `Certainty`와 `Severity`가 끝까지 분리돼 있고, 화면에서도
다른 채널로 표현한다. 선 스타일이 확실성, 색이 심각도다.

### 2. 못 읽은 글자는 절대 지어내지 않는다

OCR이 반쯤 읽고 모델이 문맥으로 메우면 그럴듯한 한국 주소와 이름이 만들어진다.
**개인정보 보호 서비스가 개인정보를 창작하는 셈**이다.

신뢰도가 임계값 아래면 `Certainty.REGION_ONLY`가 되고, `evidence_text`는
`None`으로 남는다. 화면에는 "내용을 확인하지 못했습니다"만 나간다.

### 3. 출력 문구는 한 파일에서만 만든다

`wording.py` 바깥에서 사용자용 문장을 조립하지 않는다. 단정 표현을
`assert_safe()`가 실제로 막는다. 예외를 던지지 조용히 통과시키지 않는다.

```python
BANNED = ["당신의 집", "거주지입니다", "신원이 특정됩니다", "재직 중입니다", ...]
```

"단정하지 않는다"를 주석으로만 두면 개발 중에 새어나간다. 어미를 코드에
고정해두면 급하게 문구를 추가할 때도 안 무너진다.

### 4. 위험 점수를 계산하지 않는다

k-익명성은 데이터셋 안에서 같은 준식별자 조합을 가진 레코드가 몇 개인지
세는 개념이다. 비교할 모집단이 없으면 계산이 성립하지 않는다. 사진 한 장으로
"신원 특정 가능성 87점"을 뽑을 근거는 없다.

대신 **노출 근거 + 조치 우선순위**를 낸다. 가림 권장 / 검토 권장 / 참고
세 단계이고, 판정 규칙은 `context.py`에 표로 적혀 있어 그대로 감사할 수 있다.

### 5. 다른 종이의 정보는 묶지 않는다

책상 위에 내 영수증과 룸메이트 송장이 같이 있을 때 이름과 주소를 잘못
연결하면 **존재하지 않는 사람의 프로필**을 만들어낸다.

`grouping.py`가 텍스트 조각을 공간적으로 군집화해 문서 인스턴스를 나눈다.
결합 설명은 같은 군집 안에서만 만든다.

### 6. QR 링크는 열지 않는다

서버가 임의 URL을 요청하면 SSRF 통로가 된다. 해독된 문자열만 본다.
URL이면 호스트만 떼어 보여주고 경로는 감춘다.

해독 성공과 의미 파악 성공도 구분한다. 결과가 숫자열뿐이면 운송장번호인지
회원번호인지 확정할 수 없고, 그렇게 말한다.

### 7. 가린 자리에 정보를 남기지 않고, 다시 검사한다

**글자 위에 블러를 거는 방식은 쓰지 않는다.** 전화번호·운송장번호는 글꼴과 형식이
정해져 있어서, 후보 번호를 같은 글꼴로 그려 같은 블러를 건 뒤 비교하면 맞춰진다.
모자이크(픽셀화)도 같은 방식으로 복원 시도가 가능하다(Depix 류).

가리는 방식은 두 가지이고, 둘 다 가린 자리의 원본 화소를 쓰지 않는다.

- **흐리게(기본)** — 흐린 유리처럼 보인다. 만드는 순서가 다르다.
  1. 가릴 자리를 **주변 테두리의 평균색**으로 채운다. 이 순간 글자가 사라진다.
     평균에는 다른 가릴 자리 안의 화소를 넣지 않는다.
  2. 그 상태에서 블러를 걸어 주변과 잇고, 살짝 밝게 한 뒤 옅은 결을 얹는다.
     완전히 녹아들면 받은 사람이 '원래 아무것도 없었다'고 오해할 수 있어서다.

  결과는 가린 자리 **바깥** 화소로만 만들어진다. 같은 자리에 다른 번호가 있었어도
  결과가 화소 하나까지 같다. `tests/test_redact.py` 가 이것을 확인한다.
- **검은색** — 단색으로 덮는다.

어느 쪽이든 재인코딩해서 내보내므로 원본 화소는 파일에 남지 않는다.

**기울어진 글자는 기울어진 모양 그대로** 가린다. PaddleOCR 가 주는 글자 외곽선
(`Box.poly`)을 그 축을 따라 여백만큼 넓혀서 덮는다. 축 정렬 사각형으로 가리면 30°
기울어진 송장에서 가리는 넓이가 4배가 되고 위아래 줄까지 덮인다. 실측(PaddleOCR,
송장 30°·60°): 가린 넓이가 사각형 방식의 24~26%, 다시 검사해서 남은 것 0.
다시 검사할 때 겹침도 실제 모양으로 잰다. 사각형끼리 재면 주소만 가렸을 때 그
사각형에 걸치는 옆 줄 전화번호를 '가렸는데 남았다'로 잘못 센다.

**미리 보기**는 저장할 때와 같은 함수로 가린 축소본을 서버에서 받아 보여준다.
화면에서 따로 흉내 내면 '미리 본 것'과 '저장된 것'이 달라질 수 있다. OCR 을
돌리지 않아 대기열을 거치지 않는다. 미리 보기 중에 항목을 고르거나 방식을 바꾸면
바로 다시 그린다.

그리고 **내보낼 파일을 실제로 다시 읽어 검사한다.** 캔버스에 박스만 그려놓고
원본을 그대로 내보내는 사고가 흔하다.

통과 기준은 "개수가 줄었다"가 아니라 **선택한 영역 하나하나에서 다시 탐지되는
것이 없고 위치정보가 남지 않았다**이다. 10곳 중 1곳만 가려도 개수는 준다.
선택하지 않은 곳에 남은 항목은 실패로 치지 않고 개수만 알려준다.

탐지기가 놓친 곳(얼굴, 손글씨 등)은 사진 위를 끌어서 직접 지정할 수 있다.
아무 영역도 고르지 않아도 저장할 수 있다. 위치정보만 지우고 싶은 경우가 있다.

### 8. 무상태

업로드된 이미지를 디스크에 쓰지 않고, 세션에 담지 않는다. 가림 요청 때
이미지를 다시 받는 것도 그 때문이다. 서버가 원본을 들고 있지 않다.
추출된 문자열은 어떤 로그에도 기록하지 않는다.

### 9. 한 줄로 세운다

OCR 엔진은 한 번에 하나만 돌 수 있다. 요청은 들어온 순서대로 대기열
(`jobqueue.py`)을 거치고, 화면은 번호표로 "앞에 몇 건, 약 몇 초"를 묻는다.
머리글에는 전체 대기열(처리 중 · 대기)이 늘 보인다.

- 기다리는 동안 서버는 받은 바이트만 들고 있다. 디코딩은 차례가 온 뒤에.
- 다른 사진을 넣거나, "다른 사진 넣기"를 누르거나, 창을 닫으면 기다리던 요청을
  취소한다. 아무도 보지 않을 결과를 만드느라 다른 사람이 밀리지 않게.
- 대기가 `PL_QUEUE_MAX`(기본 12) 를 넘으면 503 과 `Retry-After` 로 돌려보낸다.
- 대기열에는 번호표 문자열만 있다. 무상태 원칙은 그대로다.

## 비교 실험

주장 대신 측정한다. 같은 사진, 같은 OCR 엔진, 규칙만 바꿔 세 조건을 돌린다.

Tesseract 5.5, 합성 샘플 3장(가려야 할 항목 9개, 가리면 안 되는 항목 6개).

| 조건 | 놓침 | 오경고 |
|---|---:|---:|
| 정규식만 | 1 | 5 |
| +심각도표 | 6 | 0 |
| +문맥·결합 | 4 | 0 |

PaddleOCR(기본 설정)로는 `+문맥·결합` 이 **놓침 0, 오경고 0** 이다(아래 표).

같은 채점 기준으로 맨 처음 코드를 돌리면 `+문맥·결합` 이 놓침 9, 오경고 0이었다.
차이는 아래 "개발 중 나온 실제 버그" 8~13번과 문맥 규칙 개정(아래 "문맥 판단")에서 나왔다.

> 샘플을 이 저장소에서 다시 만들면(`python samples/make_sample.py samples/out`) 글꼴이
> 달라 PaddleOCR `+문맥·결합` 이 놓침 1 로 나온다. 위·아래 숫자는 privacy-lens-2 에
> 들어 있던 원본 샘플 이미지로 잰 것이다. 같은 이미지로 재면 두 저장소 결과가 같다.

### OCR 엔진별 (같은 규칙, `+문맥·결합` 기준)

| OCR | 놓침: 개정 전 → 같은 줄 라벨 → 윗줄 이어받기 | 오경고 | OCR 평균 ms |
|---|---:|---:|---:|
| Tesseract 5.5 | 5 → 4 → **4** | 0 | ~1500 |
| PaddleOCR 3.7 · `PP-OCRv5_server_det` + `korean_PP-OCRv5_mobile_rec` | 9 → 3 → **0** | 0 | ~3600 |
| PaddleOCR 3.7 · `PP-OCRv6_medium_det` + `korean_PP-OCRv5_mobile_rec` (기본) | 9 → 3 → **0** | 0 | ~2500 |

Tesseract 의 남은 4건은 라벨 자체를 못 읽거나(`받는분`) 도로명을 깨뜨려 읽은
경우라 규칙으로는 되살릴 수 없다.

> **0 을 그대로 믿지 말 것.** 윗줄 이어받기 규칙은 이 합성 샘플 3장의 남은 놓침을
> 보면서 만들었다. 규칙 자체는 일반적이지만(여러 줄로 이어지는 값), 이 샘플로
> 잰 숫자는 규칙을 만든 데이터로 잰 숫자다. 개발에 쓰지 않은 실사 사진으로 다시 잴 것.

규칙 개정 전에는 PaddleOCR 가 글자를 더 정확히 읽는데도 놓침이 더 많았다.
문맥 반경이 '상자 높이 × 6' 인데 PaddleOCR 상자가 커서 반경이 ~144px 까지 늘고,
아래쪽 `고객센터` 가 모든 항목의 반경에 들어와 "양쪽 다 있음 → 검토 권장" 이
전부를 내렸다. 같은 줄 바로 옆에 `연락처` 가 있는데도.

같은 줄 라벨 규칙 뒤에 남았던 3건은 전부 **동·호수 줄**이었다. 주소 둘째 줄이라
자기 라벨이 없고, 위 `배송지`(~31px)와 아래 `고객센터`(~60px)의 거리 차가 '절반 이하'
기준에 조금 못 미쳤다. 거리 기준을 늘려 맞추는 대신 '윗줄 라벨 이어받기'를 넣었다.

채점은 놓침과 오경고 모두 **숫자열 완전 일치**로 센다. 이전에는 놓침만 부분
일치로 느슨하게 셌고, 숫자가 없는 항목이 빈 문자열이 되어 `"" in target` 이
항상 참이 되는 버그가 있었다. 이전 표의 숫자는 그 기준으로 나온 것이라 버렸다.

- **놓침** — 가려야 할 항목을 가림 권장으로 못 올린 횟수
- **오경고** — 고객센터 번호·운송장번호를 가림 권장으로 올린 횟수

소박한 정규식은 다 잡지만 쓸 수 없을 만큼 시끄럽다. 심각도표만 넣으면
조용해지는 대신 놓침이 뛴다. 문맥을 보면 오경고 0을 유지하면서 놓침을 되돌린다.

> **이 숫자를 발표에 쓰지 말 것.** 합성 샘플 3장 기준이고, 파이프라인이 도는지
> 확인하는 용도다. 발표용 숫자는 **개발에 쓰지 않은 실사 사진**으로 다시 뽑아야 한다.
> 그리고 베이스라인은 가급적 PaddleOCR + Presidio 같은 **공개 구현**으로 잡아라.
> 직접 만든 대조군은 "일부러 약하게 잡은 것 아니냐"는 반박을 부른다.

### 회전 (`python -m eval.rotation`, PaddleOCR)

합성 송장 3종 × 원본/책상 사진을 돌린다. 각도당 정답 18개(전화·주소·동호수), 이름 6개.

| 각도 | OCR 이 읽은 정답 | 가림 권장 (이전 → 지금) | 이름 (이전 → 지금) | 오경고 |
|---:|---:|---:|---:|---:|
| 0° | 17 | 17 → 17 | 5 → 5 | 0 |
| 15° | 18 | 18 → 18 | 6 → 6 | 0 |
| 30° | 18 | 12 → **18** | 0 → **6** | 0 |
| 45° | 18 | 11 → **18** | 0 → **6** | 0 |
| 60° | 18 | 8 → **18** | 0 → **6** | 0 |
| 90° | 18 | 4 → **12** | 0 → **4** | 0 |
| 180° | 12 | 8 → **12** | 0 → **3** | 0 |
| 270° | 18 | 14 → **18** | 0 → **6** | 0 |
| 합계 | 137/144 | 92 → **131** | 11 → **42** /48 | 0 |

'이전'은 '같은 줄·왼쪽·윗줄'을 화면 가로·세로로 재던 때다. 30° 만 기울어도 같은 줄
라벨이 48px 위에 찍혀 '다른 줄'이 됐고, 60°·90° 에서는 `배송지`·`고객센터` 를 사람
이름으로 잡기까지 했다. 지금은 글줄 좌표계(`pipeline/layout.py`)로 잰다.

남은 놓침은 전부 OCR 이 라벨이나 이름을 아예 못 읽은 경우다(90° 1종, 180° 3장, 0° 1장).
`tests/test_layout.py` 는 같은 서식을 15°~270° 로 돌려도 판정이 0° 와 같은지 본다.

## 합성 데이터

명찰·송장이 라벨링된 공개 데이터셋은 없다. `samples/make_sample.py`가
템플릿에 가짜 정보를 채우고 원근 변환으로 배경에 합성한다. 좌표를 알고 있으니
라벨이 자동으로 나온다.

샘플에는 **오탐 함정**이 일부러 들어 있다. 같은 종이에 수취인 연락처와
고객센터 번호가 둘 다 있다. 정규식만 쓰면 둘 다 경고한다.

두 가지 주의:

- **분할은 템플릿 단위로.** 같은 템플릿의 변형본이 학습과 평가에 섞이면 누수다.
- **촬영 편향.** 팀원이 찍으면 "여기 송장 넣어야지" 하며 잘 보이는 각도로 찍는다.
  촬영자와 평가 설계자를 분리하거나, "평소처럼 방 사진 찍어줘"라고만 부탁하고
  나중에 라벨링하는 게 낫다.

### 문맥 판단

같은 `010-1234-5678`이라도 주변 문구로 갈린다.

```
1. 같은 줄 바로 왼쪽 라벨이 정한다          서류는 거의 '라벨: 값' 꼴이다
   '연락처  010-…'                       →  가림 권장
   '고객센터  1588-…' / '대표전화 010-…'  →  참고
   멀리 있는 다른 단어는 보지 않는다

   자기 라벨이 없으면 바로 윗줄(왼쪽 정렬, 줄 간격 이내)의 라벨을 이어받는다
   '배송지  서울특별시 강남구 권선로 208
            130동 1343호'               →  '배송지' 를 이어받아 가림 권장
   라벨이 값 위에 있는 서식('받는 분' 아래 이름), 세 줄 주소까지

2. 라벨이 없으면 반경 안의 단어를 본다
   '수취인' '받는분' '배송지' … 만          →  가림 권장
   '고객센터' '대표번호' '문의' … 만        →  참고
   둘 다 있고 한쪽이 절반 이하 거리         →  가까운 쪽
   둘 다 있고 거리가 비슷                   →  검토 권장 (단정하지 않음)
```

'같은 줄 바로 왼쪽'은 같은 조각 안에서 값 바로 앞(Tesseract 가 `받는분 010-…` 을
한 줄로 합칠 때)이거나, 같은 줄 왼쪽에서 가장 가까운 조각(PaddleOCR 가 따로 줄 때)이다.
그 조각이 라벨이 아니면 더 왼쪽으로 가지 않는다. 라벨 끝이 두 어휘에 다 맞으면
긴 쪽이 이긴다(`대표전화` 는 `전화` 로도 끝나지만 공개 쪽).

공백을 다 빼고 비교한다(Tesseract 는 `연락처`를 `연 락 처`로 준다). 공개 쪽 단어
안에 들어 있는 개인 쪽 단어(`대표전화` 속 `전화`)는 개인 신호로 세지 않는다.
판정 코드는 `context._judge()` 한 곳에 있다. 절반 기준은 `CLEARLY_CLOSER`.

'같은 줄', '왼쪽', '윗줄', 거리는 화면 가로·세로가 아니라 **글줄 좌표계**로 잰다
(`pipeline/layout.py`). PaddleOCR 외곽선의 긴 축이 글줄 방향이다. 축의 앞뒤는 문서의
주된 축에 맞추고, 뒤집힌 문서(180°)는 '라벨이 값보다 앞에 온다'로 투표해서 가린다.
외곽선이 없으면(Tesseract) 화면 가로·세로 그대로라 예전 계산과 같다.

Presidio가 독일 우편번호를 다루는 방식이 같은 발상이다. 패턴만으로는 오탐
위험이 커서 주소 문맥 단어가 함께 있을 때만 신뢰하고 기본 신뢰도를 낮게 둔다.

## 개발 중 나온 실제 버그

기록해둔다. 같은 걸 또 밟지 않으려고.

1. **줄 병합이 어순을 뒤집었다.** 기울어진 종이에서는 OCR 조각이 좌→우로 오지
   않는다. `받는 분`이 `는 분 받`이 됐다. 행마다 x로 재정렬해서 해결.

2. **Tesseract가 한글을 낱글자로 쪼갠다.** `권선로` → `권 선 로`. 이러면 주소
   정규식이 하나도 안 걸린다. `kr_patterns.normalize()`가 낱글자 한글을 다시 붙인다.
   "정규식으로 되는 걸 왜 AI라고 하나"의 답이 여기 있다. 정규식은 깨끗한
   문자열에서만 동작한다.

3. **`121동 1655호`를 차량번호판으로 오탐했다.** 번호판에 쓰이는 한글은 정해져
   있다(가나다라마 거너더러머 고노도로모 하허호 배 등). 동·호는 거기 없다.

4. **조사 오류.** `문자열가 인식됨`. 한글 종성 판정 함수를 넣었다.

5. **리눅스 폰트 경로를 박아뒀다.** Windows에서 `OSError: cannot open resource`.
   `samples/fonts.py` 가 운영체제별 후보를 훑고, 없으면 폰트 폴더를 뒤진다.
   Tesseract 경로도 같은 문제가 있어 `pipeline/ocr.py` 에 탐색을 넣었다.

6. **PaddleOCR 2.x API로 짰다.** 3.x에서 `ValueError: Unknown argument: show_log`.
   생성자 시그니처를 들여다보고 지원 인자만 넘기도록 바꿨다. 결과 파서도 두 형식을
   다 받는다.

7. **numpy 배열에 `or []` 를 썼다.** 3.x의 `rec_scores` 는 numpy 배열인데
   `arr or []` 는 `ValueError: The truth value of an array ... is ambiguous` 를 낸다.
   `None` 검사로 바꿨다. 외부 라이브러리 결과에 파이썬 기본 진리값 판정을
   쓰면 안 된다는 교훈.

8. **같은 줄의 라벨을 문맥으로 못 썼다.** 줄 병합이 `받는분 010-…` 을 한 조각으로
   만드는데, 문맥 검색이 자기 조각을 빼고 주변만 봤다.

9. **`연 락 처` 는 `연락처` 가 아니었다.** 문맥 어휘를 낱글자로 쪼개진 원문에
   그대로 맞췄다. 공백을 다 빼고 비교한다.

10. **운송장번호 안에서 전화번호를 찾았다.** `5301012345678` 가운데의 `01012345678`.
    전화번호 정규식에 숫자 경계(`(?<!\d)…(?!\d)`)를 넣었다.

11. **주소 윗줄과 동·호수 아랫줄이 한 줄로 섞였다.** Tesseract 가 `구`·`선로` 에
    두 배 큰 상자를 주는데 같은 줄 판정을 큰 쪽 높이로 했다. 작은 쪽으로 바꾸고,
    처리 순서를 타지 않게 union-find 로 잇는다.

12. **2020년 10월 이후 주민등록번호를 버렸다.** 뒷자리가 임의번호라 체크섬이 안
    맞는다. 구분자가 있으면 `rrn_unverified` 로 남긴다. 구분자 없는 13자리까지
    받으면 앞 6자리가 날짜처럼 보이는 운송장번호를 잡는다(테스트가 잡아냈다).

13. **결합 설명이 다른 종이의 정보를 섞을 수 있었다.** 군집 외곽 사각형 포함으로
    소속을 정했는데, 비스듬히 겹친 두 종이는 사각형끼리 겹친다. 조각 번호로 정한다.

14. **세로 사진이 누운 채 저장됐다.** EXIF 회전 태그를 반영하지 않고 분석한 뒤,
    내보낼 때 EXIF 를 지웠다. 이제 열 때 `exif_transpose` 한다.

15. **`PL_TESSERACT` 가 동작하지 않았다.** 자동 탐색이 실패하면 환경변수를 보기 전에
    예외를 던졌다.

16. **OCR 이 이벤트 루프를 막았다.** `async def` 안에서 동기 OCR 을 돌려 요청 하나가
    서버 전체를 세웠다. 엔드포인트를 `def` 로 바꿔 스레드풀에서 돈다.

17. **PaddleOCR 추론기가 스레드 안전하지 않았다.** 16번에서 엔드포인트를 스레드풀로
    옮기자, 동시에 들어온 두 요청이 한 엔진을 같이 써서 `Broadcast dimension mismatch`
    로 죽었다(서로 다른 사진의 중간 텐서가 섞임). 엔진마다 잠금을 두고 한 번에 하나씩
    돌린다. Tesseract 는 호출마다 별도 프로세스라 문제가 없었다.

18. **`paddlepaddle` 없이 `paddleocr` 만 깔려 있었다.** 모델을 다 받은 뒤에야
    `paddle_static` 엔진이 없다며 멈췄다. 깔고 나니 3.3.1 이 CPU(oneDNN) 추론에서
    `NotImplementedError` 로 죽었다. 3.2.2 로 내려 해결. `run.py --check` 가 이제
    `paddlepaddle` 도 확인한다.

19. **1MB 넘는 업로드가 디스크에 쓰였다.** Starlette 는 업로드를 `SpooledTemporaryFile`
    로 받는데 1MB 를 넘으면 임시 파일로 넘긴다. 휴대폰 사진은 거의 다 넘는다.
    "디스크에 쓰지 않는다"는 원칙이 처음부터 조용히 깨져 있었다. 한도(25MB)까지는
    메모리에 두도록 `MultiPartParser.spool_max_size` 를 올렸다.

20. **라벨에 붙은 숫자를 하나도 못 찾았다.** 주민등록번호·카드·사업자번호·긴 숫자
    정규식이 `\b` 로 경계를 잡았는데, 파이썬 `\b` 는 한글을 단어 글자로 친다.
    PaddleOCR 가 공백을 빼먹은 `운송장번호909266858784`, `주민번호900101-…` 에서
    `호`와 `9` 사이에 경계가 없다고 보고 통째로 지나쳤다. 전화번호(10번)처럼
    '앞뒤가 숫자가 아님'으로 바꿨다. 같이 고친 것: `6123-4567-8901` 처럼 하이픈으로
    끊은 긴 숫자를 받고, `운송장번호` 라벨 옆의 긴 숫자는 '운송장번호로 보이는 숫자'
    (검토 권장)로 부른다. 같은 번호가 든 바코드·QR 이 이미 검토 권장이라 맞췄다.
    라벨이 없으면 여전히 정체를 단정하지 않는다(설계 원칙 6).

## 알려진 한계

- **Tesseract 한국어가 약하다.** 라벨(`받는분`, `배송지`)을 아예 못 읽거나
  `백 송 / 지` 처럼 깨뜨리면 문맥이 사라져 검토 권장에 머문다. 도로명을
  `SST ASE` 처럼 읽으면 주소 자체를 못 잡는다. 현재 놓침 5건이 대부분 여기서 나온다.
  PaddleOCR로 바꾸면 개선될 가능성이 크지만 측정해봐야 안다.
- **"내용 확인 불가" 탐지는 사실상 정규식에 걸린 흐린 글자뿐이다.** 문서·카드의
  모양을 찾는 검출기가 없다. 설계 원칙 1번의 "흐릿한 학생증"은 지금 구조로는
  잡히지 않는다. 글자를 못 읽으면 영역도 못 낸다.
- **이름은 라벨이 있을 때만 잡는다.** 명찰처럼 라벨 없이 이름만 크게 쓰인 경우는
  놓친다. 라벨 없이 잡으면 오탐이 감당이 안 된다.
- **종이 두 장이 맞닿아 있으면 한 문서로 묶인다.** 군집은 글자 간격만 본다.
- **기울어진 송장의 판단은 OCR 이 라벨을 읽어야 성립한다.** 회전 실험에서 남은
  놓침은 전부 OCR 이 라벨(`받는분`·`연락처`, 작은 회색 글자)이나 이름 자체를 못
  읽은 경우다. 라벨이 하나도 없고 `고객센터` 같은 공개 쪽 단어만 읽히면 전화·주소가
  참고로 떨어진다.
- **라벨 글자에 OCR 잡음이 끼면 놓친다.** 30° 기울어진 JPEG 에서 PaddleOCR 가
  `받는분` 을 `받-는분` 으로 읽어, 이름(`박민준`)을 읽고도 라벨을 못 찾아 놓쳤다.
  라벨 비교 전에 기호를 걷어내는 정규화가 필요하다(백엔드 할 일).
- **한 사진에 방향이 크게 다른 종이가 섞이면** 읽는 방향 추정이 한쪽에 맞춰진다.
  문서 전체의 주된 축 하나로 각 줄의 앞뒤를 맞추기 때문이다.
- **정확하게 가리는 만큼, 놓친 건 그대로 보인다.** 예전 축 정렬 사각형은 넓어서
  탐지하지 못한 옆 글자(예: 기울어진 송장의 이름)까지 우연히 덮었다. 이제 찾은
  모양만 가리므로 저장 전에 미리 보기로 확인하고, 놓친 곳은 직접 끌어서 지정할 것.
- **기울어진 QR은 원본 해상도에서 자주 실패한다.** 배율 1.0/1.6/2.4를 훑어
  잡고 있고, 그만큼 처리 시간이 늘어난다.
- **배경의 작은 글씨.** 타일 분할 검사를 실험해볼 만하지만, 처리 시간이 늘고
  원본에서 이미 뭉개진 글자가 복원되지는 않는다. 효과를 측정하고 판단할 것.
- **브라우저 내 처리 미구현.** 현재는 서버 처리다. ONNX Runtime Web 이전이 로드맵.
- **이름.** `Privacy Lens`는 미시간대 연구(PoPETs 2024)와 AI Tinkerers 출품작이
  이미 쓰고 있다. 후보를 고르면 도메인과 상표를 직접 확인할 것.
