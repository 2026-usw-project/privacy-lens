## 3. 미결 사항

상태는 모두 **미결**입니다. '논의'는 결정에 참여할 역할 번호입니다.

### D-01 스키마를 OCR 우선에 맞게 고칠지

- 현황: `Finding`이 `Detection`을 상속해 `label`(9종)과 `det_conf`가 필수이고, 흐름이 `detect → read_and_judge`(객체 검출 → 크롭 OCR)입니다.
- 쟁점: OCR 우선에서는 객체 검출 없이 "개인정보 항목 + 위치"만 나올 수 있어 지금 구조에 담기지 않습니다. 발표용 근거 문장("택배 송장에서 …")도 객체 종류를 알아야 만들 수 있습니다.
- 선택지: (a) `label`·`det_conf`를 선택값으로 완화 (b) 항목 중심 목록을 새로 두고 객체 정보는 선택 필드로 (c) 현행 유지하고 객체 검출을 일찍 도입
- 후속: 결정되면 `SCHEMA.md`의 흐름도와 담당 표(A/B/D 표기)도 함께 고칩니다.
- 논의: 4(주담당)·3·5, 정답 형식을 맞추기 위해 1·2

### D-02 평가가 읽을 출력 경로

- 현황: API 응답에는 마스킹된 `value_masked`만 있고 OCR 원문(`ocr`)은 debug 모드에서만 나옵니다.
- 쟁점: 문자열까지 맞았는지 보는 평가는 마스킹된 응답만으로는 할 수 없습니다.
- 선택지: (a) 평가 코드가 AI 모듈 함수를 직접 호출 (b) debug 응답 사용 (c) 정답에도 같은 마스킹 규칙을 적용해 비교(정보 손실)
- 논의: 2·3

### D-03 정답 형식과 응답 형식의 매핑

- 현황: 정답은 박스 또는 다각형과 판독 3단계(읽힘·일부·불가)로 만들 예정입니다. 스키마의 개인정보 위치(`PIIItem.bbox`)는 정수 사각형뿐이고, 판독 상태는 수치(`readability`)뿐입니다.
- 쟁점: '찾았다고 인정할 조건'을 정해야 평가할 수 있습니다. 위치 일치 기준(IoU 임계값, 다각형 → 사각형 변환)과 판독 상태의 표현이 필요합니다.
- 논의: 1·2·3

### D-04 성공 지표 정비

- mAP@0.5(80%)는 객체 검출기를 전제로 한 목표입니다. OCR 우선이면 항목 단위 정밀도·재현율이 주 지표이고, mAP는 객체 검출을 도입할 때만 의미가 있습니다.
- 발표안은 "10px 이하 글자 판독"을 검증한다고 했지만 기준표에 수치 목표가 없습니다.
- 비위험 사진 100장이 실사 300장에 포함되는지 별도인지, "실사 200~300장 확보 / 최종 평가 300장 목표"의 기준이 무엇인지 정리가 필요합니다.
- 논의: 1·2

### D-05 가림 처리와 EXIF 제거를 어디서 할지

- 현황: `SCHEMA.md` §5와 발표안은 브라우저 Canvas에서 처리합니다(다시 인코딩하면 EXIF가 빠짐). 분담안은 백엔드(4번)가 최종 좌표로 가리고 EXIF를 제거해 다운로드 API로 제공합니다.
- 영향: 4·5번의 범위, 2번의 통합 테스트(화면 박스 ↔ 결과 파일). 서버가 수정된 좌표로 처리하려면 원본을 편집·다운로드가 끝날 때까지 임시 보관하거나 다시 받아야 하므로, "분석 후 즉시 파기" 원칙의 표현도 바뀝니다.
- 논의: 4·5 (2는 참고)

### D-06 외부 OCR API를 쓸지

- 현황: 발표안은 PaddleOCR·외부 OCR API·Tesseract를 비교한 뒤 정하기로 했습니다.
- 쟁점: 외부 API를 쓰면 사용자의 사진이나 크롭이 제3자 서버로 전송됩니다. 개인정보를 지키는 서비스의 취지와 '원본 비저장' 원칙에 어긋날 수 있습니다.
- 선택지: (a) 로컬 OCR만 사용 (b) 외부 API는 가상 정보 사진으로 비교 실험에만 쓰고 서비스 경로에서는 제외 (c) 사용자 동의와 전송 범위 제한을 두고 사용
- 논의: 3·4 + 팀 전체

### D-07 EXIF 제거 검증용 샘플을 누가 만들지

- 현황: EXIF 제거율 100%는 자동 검사 스크립트로 확인하기로 했지만, GPS·기기 정보가 들어 있는 테스트 사진을 만드는 담당이 분담안에 없습니다.
- 제안: 가짜 GPS를 piexif로 넣은 JPEG 세트를 평가 스크립트와 함께 만든다. 1·2번이 맡는 것이 자연스럽습니다(제안일 뿐 결정 아님).
- 논의: 1·2·4

### D-08 데이터 공유 방식

- 현황: `.gitignore`가 사진 확장자와 `data/raw`·`data/real`·`data/synthetic`을 막고 있어 사진을 git으로 공유할 수 없습니다.
- 쟁점: 공유 위치(드라이브 등), 출처·사용 조건을 적는 목록(manifest), 라벨 파일(텍스트, 가상 정보만)을 git에 둘지.
- 논의: 1·2

### D-09 일정 재조정

- 현황: P0~P6(7주)은 YOLO·합성 데이터 우선 계획이고 시작일이 문서에 없습니다. 분담안은 첫 주 목표를 "사진 한 장의 end-to-end 처리"로 제시합니다.
- 쟁점: 합성 생성기·YOLO 학습(P1~P2)이 조건부가 되면 단계와 마일스톤이 바뀝니다.
- 논의: 전원

### D-10 탐지·평가 범위

- 현황: 발표안은 9종 객체 안의 글자만 대상으로 했습니다. OCR 우선이면 사진 전체의 글자를 읽으므로 9종 밖(포스트잇, 손글씨, 상자에 직접 쓴 주소 등)도 잡힐 수 있습니다.
- 쟁점: 정답·평가에 9종 밖 항목을 포함할지에 따라 재현율 85%의 분모가 달라집니다.
- 논의: 1·2 + 팀

### D-11 위험도 산식

- 유형 × 판독가능성 × 면적의 가중치와 등급 임계값(스키마 초기값: none 0, low < 0.3, medium 0.3~0.6, high ≥ 0.6)을 3번이 확정합니다. 확정하면 PRD FR-05와 `SCHEMA.md`에 기록합니다.
- 논의: 3 (2는 측정)

### D-12 가림 기준표 확정

- 현황: [MASKING_CRITERIA.md](MASKING_CRITERIA.md) 초안(2026-11-01). `eval/judgment.py` 정답과 `samples/props.py` 소품 정답이 이 초안을 따른다.
- 쟁점: 라벨 없는 이름 후보를 '확인 필요'로 올릴지(놓침↓ 오탐↑), 학교·회사명 단독, 메신저 대화방 이름, 일부 가려진 카드번호.
- 측정(2026-11-01, 가상 데이터): 단서 있는 라벨 없는 이름은 이미 가림 권장으로 구현(`PL_UNLABELED_NAMES=context`, 기본).
  남은 쟁점은 **단서 없는 이름 후보**뿐이다. `all` 로 켜면 가상 장면의 '가리면 안 될 것' 182개 중 8개(4.4%)가 잘못 확인 요청되고,
  따로 모은 일반 낱말 95개 중 12개(13%: 지하철·옥수수·모바일 등)가 이름 후보가 된다. 실사 한 장에 낱말이 수십 개면 장당 몇 개씩 생길 수 있다.
  `python -m eval.judgment --unlabeled-names all`, `python -m eval.names_check`.
- 논의: 전원. 정해지면 기준표·`eval/judgment.py`·`samples/props.py` 를 함께 고치고 `eval.judgment --update`.

### D-13 '가림' 등급을 화면에서 기본 선택할지

- 현황: 화면은 모든 탐지 항목을 기본 해제로 둔다(`web/frontend-demo/dist/core.js` `enabled:false`, 안내 문구 "기본으로 아무것도 고르지 않았어요"). 문서화된 결정은 없다.
- 쟁점: 기준표 원칙 2(놓침이 오탐보다 나쁨)와 맞추려면 '가림'은 기본 선택, '확인 필요'는 해제가 자연스럽다. 반대로 기본 해제는 사용자가 하나씩 확인하게 만든다.
- 참고: 지금 화면에서 가림 권장 항목만 체크한 모습을 캡처해 팀에 공유함(2026-11-01). 코드는 바꾸지 않았다.
- 논의: 5 + 전원

### D-14 서버가 쓸 YOLO 모델

- 현황: 학습 도구는 실사로 검증된 모델만 `current.txt` 로 올린다(2026-11-01부터 val·test 0장이면 교체 안 함). 서버(`pipeline/detect.py`)는 `current.txt` 가 아니라 프로젝트 `models/` 의 **가장 큰 버전 폴더**를 쓴다(PR #20).
- 쟁점: 검증 안 된 새 버전을 `models/` 에 복사하면 서버가 바로 그것을 쓴다. 시연 서버는 `PL_YOLO_WEIGHTS` 로 고정할지, 서버도 `current.txt` 를 따르게 할지.
- 논의: 3·4

### D-15 개발자 모드의 LLM 판단과 외부 전송 (2026-11-01)

- 정한 것: 화면의 판정 조건(문맥·결합 / 심각도표 / 정규식만)을 없애고 **문맥·결합만** 쓴다. 대조군 함수(`naive_regex`, `baseline`)는 비교 실험용으로 `pipeline/analyze.py`·`eval` 에 남긴다.
- 정한 것: **개발자 모드**에서 판단 모델을 고른다(규칙 기반 / ChatGPT / Gemini / Claude / OpenRouter / Ollama / Custom API, `pipeline/llm_judge.py`). LLM 을 고르면 규칙 판단은 돌지 않고 글자 판단을 모두 LLM 이 한다. 위치정보·QR·YOLO 영역 검사는 그대로이고, 저장 뒤 재검사도 같은 판단 방법을 쓴다.
- 예외: 클라우드 공급자(ChatGPT·Gemini·Claude·OpenRouter, 또는 이 컴퓨터가 아닌 주소의 Ollama·Custom)를 고르면 **OCR 원문이 그 회사 서버로 전송된다.** AGENTS.md 의 '외부 API 로 내보내지 않는다' 규칙의 유일한 예외다. 기본값은 규칙 기반이고, 화면에 전송 경고를 띄운다. 실사 개인정보 사진에는 쓰지 않는다.
- 키: 브라우저 localStorage(`pl.devMode`)에만 저장한다. 요청마다 로컬 서버로 보내고, 서버는 저장·로그하지 않으며 오류 문구에도 넣지 않는다. 키는 URL 이 아니라 헤더로 보낸다.
- 지키는 것: LLM 이 준 근거 문자열이 OCR 조각 안에 없으면 조각 원문을 쓴다(지어낸 글자를 보여 주지 않음). 사진에 없는 라벨은 근거로 쓰지 않는다. 화면 문구는 `wording.py` 가 만든다. OCR 신뢰도가 낮은 조각은 지금처럼 내용 없이 영역으로만 낸다.
- 측정하지 않은 것: LLM 판단의 정확도·속도·비용은 재지 않았다. 비교하려면 `eval.judgment`·`eval.failures` 에 LLM 경로를 붙여야 한다.
- 결정: 요청자(개발자 모드 도입). 팀 공유 필요: 1·2·3
- 추가(2026-11-01): LLM 에 조각마다 글줄 관계(`line`·`order`·`left`·`above`, 규칙과 같은 `layout.py` 계산)와 문서 묶음(`doc`)을 함께 보낸다. LLM 은 근거를 자유 낱말(`near`) 대신 종류(`basis`: label·document·linked·honorific·format)와 조각 번호로 답하고, 서버가 라벨이 실제로 옆에 있는지(같은 줄 앞·윗줄·문맥 반경)와 다른 개인정보 값이 아닌지 확인한다. 확인되지 않으면 근거 없이 형식 문구로 내린다. 화면 문구에는 라벨 조각 글자·문서 종류·함께 있는 항목의 종류만 들어간다(다른 값은 넣지 않음). 좌표는 LLM 에게 받지 않고 OCR 좌표로 만든다. 여러 조각으로 나뉜 값은 한 항목으로 묶는다.
- 추가(2026-11-01): LLM 판단 때 서버가 공급자와 주고받은 요청·응답(`llm_trace`)을 응답에 실어 보내고, 화면이 **브라우저 개발자 콘솔(F12)에만** 찍는다. 보낸 OCR 원문이 들어 있지만 이미 Raw OCR 로 화면에 오는 내용이고, 저장하지 않는다. 키는 끝 4글자만 남긴다. 서버 로그에는 넣지 않는다.

### D-16 YOLO 역할 전환(이미지 객체)과 YOLO26 (2026-11-02)

- 근거: 팀 실사 시험(노트북·책장이 있는 장면, 책장 위에 신분증을 눈에 안 띄게 둠)에서 **YOLO 없이 OCR 만으로** 신분증 글자까지 읽혔다.
  이전에 합성 생성기 3을 만든 계기('책장 속 작은 신분증을 놓침')와 같은 유형이다. 사진 1장이라 먼 거리·기울기·메신저 압축 사진으로
  2~3장 더 확인하고, 그 사진을 실사 평가 폴더에 정답과 함께 넣어 회귀 시험으로 쓴다(`eval.failures`, `PL_YOLO=off`).
- 정한 것: YOLO 는 **글자가 아닌 이미지 객체** 쪽으로 옮긴다. 문서 클래스(waybill·id_card·name_tag·screen)는 지금 모델로 **동결**하고 새 학습 투자는 하지 않는다.
  잃는 것: 글자를 못 읽은 카드·명찰을 영역으로 알리던 안전장치(`document`·`region_only`)가 약해진다.
- 정한 것: 학습 기본 모델을 **YOLO26n** 으로 바꾼다(`vision/train.py` `DEFAULT_BASE`, `ultralytics>=8.4`). YOLO11 모델은 이어서 학습할 수 없어 다음 학습은 `yolo26n.pt` 부터 새로 하고,
  실사 검증 사진이 없으므로 첫 YOLO26 모델만 `--force` 로 올린다. YOLO26 의 장점(CPU 추론 최대 43% 빠름, 작은 물체 라벨 할당)은 COCO 기준 공식 수치이고 우리 데이터로 잰 것이 아니다.
- 미결: 새 이미지 객체 클래스. 후보와 데이터 —
  얼굴(학습된 검출기를 쓰면 학습 불필요. **어떤 얼굴을 가릴지 정책이 먼저**: 배경의 모르는 사람만인지),
  차량 번호판(Open Images 'Vehicle registration plate'), 부대마크·보안 표식(공개 데이터 없음, 합성 필요, 2차 권장).
  `vision/classes.py` 는 맨 뒤에만 추가한다.
- 논의: 3 + 전원
